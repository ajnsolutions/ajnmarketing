**Current active initiative:** Queue Project Memory validation hardening (branch `fix/queue-project-memory-auto-repair`, PR [#108](https://github.com/ajnsolutions/ajnmarketing/pull/108), open, not yet merged). This is a direct response to the queue's first real, live, multi-task run: Task 003 started, resolved its base to `origin/main`, fully implemented its scoped work, and fully updated `.ai/CURRENT_STATUS.md`/`.ai/STATUS.json`/`.ai/HANDOFF.md`/`.ai/ROADMAP.md` in one commit — then committed, pushed, and opened a real PR (#107, now merged), exactly as its own injected prompt instructed. `run-queue.ts`'s own post-task check then failed it anyway: "task 003 failed: no project-memory update." **Root cause:** the check (`git status --porcelain -- .ai/CURRENT_STATUS.md ...`) only ever detects UNCOMMITTED changes; Task 003's agent had already committed everything, so the working tree was clean and the check saw nothing — a pure detection bug, not a real omission (verified directly from `git show --stat` on the real commit, `gh pr view 107`, and the agent's own `is_error:false` report). See `.ai/DECISIONS.md` ADR-0017 for the full incident and fix.

**What this branch (PR #108) does:** `scripts/ai/projectMemory.ts` (new) replaces the uncommitted-diff-only check with one that detects a real memory update whether committed or not (union of commits-since-branch-point and any uncommitted diff), rejects trivial/timestamp-only/conflict-marker/invalid-JSON updates, and adds a bounded auto-repair loop (reusing `queue.max_repair_attempts`) that re-invokes the agent with a narrow, scope-limited prompt before giving up. The subsequent commit/push/PR steps in `attemptTask()` were made idempotent (won't error if the agent already committed/pushed/opened its own PR). A permanent recovery path (`reconcileFailedMemoryChecks` in `reconcile.ts`, wired into `npm run ai:queue:reconcile` and every queue startup) reconciles any task mis-failed this exact way, provided a real PR exists and independently re-validates. A related pre-existing bug (`finalizeCompletionState()`'s multi-line commit messages losing their newlines when run through a shell) was found live during recovery and fixed alongside it.

**Task 003's recovery (historical):** its `QUEUE_STATUS.json` completion state was corrected via the existing, already-tested `finalizeCompletionState()` path — no feature work was redone. That correction shipped as part of PR #107, which is now merged. Tasks 004 and 005 remain `pending` and have not started.
